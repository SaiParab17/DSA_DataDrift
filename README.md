# DataWatch --- Statistical Data Drift & Data Quality Monitoring

DataWatch is a lightweight data-monitoring application that compares a
**reference dataset** with a **current dataset** to identify
distribution changes and common data-quality problems. It combines a
custom statistical drift engine with **Great Expectations (GX)**-based
validation and presents the results in a Neo-Brutalist web interface.

> **Current scope:** The implemented core is CSV-based statistical drift
> detection and data-quality validation. Do not assume model-impact
> analysis, persistent history, authentication, scheduled production
> monitoring, or database-backed storage exists unless it has been added
> separately.

## Overview

Data pipelines can continue running even when incoming data changes or
contains invalid values. DataWatch helps answer two separate questions:

1.  **Data quality:** Does the current dataset satisfy the configured
    validation rules?
2.  **Data drift:** Has the current dataset's feature distribution
    changed compared with the reference dataset?

These checks are independent. A dataset can pass quality checks while
exhibiting drift, or have a similar distribution while containing nulls,
duplicates, or invalid values.

## Core features

### Statistical data-drift detection

-   **Population Stability Index (PSI)** for numerical feature
    distributions.
-   **Kolmogorov--Smirnov (KS) statistic and p-value** for numerical
    distributions.
-   **Wasserstein distance** for numerical distributions.
-   **Jensen--Shannon (JS) divergence** for categorical distribution
    comparisons and other comparisons where implemented.
-   Reference-versus-current distribution visualizations.
-   Feature-level status and severity.
-   Configurable PSI threshold (the current interface shows `0.25` by
    default).

### Data-quality validation

The backend uses Great Expectations for checks that include:

-   Required-column existence.
-   Null-value validation.
-   Numeric range validation.
-   Data-type checks.
-   Row-count comparison.
-   Identifier uniqueness / duplicate checks where applicable.

The exact checks and results depend on the uploaded files and rules
generated by the backend.

### Identifier-aware column handling

DataWatch distinguishes these column roles:

-   **Numeric:** suitable for numerical statistical comparisons.
-   **Categorical:** compared using category frequencies and JS
    divergence.
-   **Identifier:** checked structurally, such as for nulls and
    duplicates, rather than treated as a meaningful continuous
    measurement.

Identifier detection is heuristic; verify its behavior for unfamiliar
column names.

## How it works

``` text
Reference CSV ─────┐
                   ├──> FastAPI backend
Current CSV ───────┘          |
                              ├──> Drift engine
                              |      ├── Numerical: PSI, KS, Wasserstein, JS
                              |      └── Categorical: JS divergence
                              |
                              └──> Great Expectations validation
                                     ├── Required columns
                                     ├── Null and type checks
                                     ├── Range checks
                                     └── Row count / identifier checks
                                              |
                                              v
                                      Combined API response
                                              |
                                              v
                                        React Results UI
```

The reference dataset acts as the baseline. The current dataset is
compared with that baseline and independently checked against
data-quality expectations.

### Thresholds

Thresholds are configuration choices, not universal scientific
constants. The PSI threshold `0.25` shown in the interface is a project
setting. Configure and document categorical JS warning thresholds
separately.

## Data-quality validation

DataWatch returns the outcome of each validation check and shows
expected versus observed values.

The quality score displayed by the current interface follows this
general calculation:

``` text
quality score (%) = passed checks / checks included in score × 100
```

Confirm in the backend how skipped or not-applicable checks are handled
for a specific run.

### How numeric range boundaries work

Range boundaries are intended to be generated by the current backend
validation implementation using information from the reference dataset.
Do not assume they are fixed universal limits. To state the exact
formula, inspect the range-generation function and identify whether it
uses mean/standard deviation, quantiles, or another method.

A statistically derived range is not automatically a business rule. A
salary may be statistically unusual without being invalid in the real
world.

## Technology stack

The project architecture uses the following technologies; check the
repository for exact installed versions:

-   **Frontend:** React, TypeScript, Vite, and the UI libraries
    configured in the project.
-   **Backend:** Python and FastAPI.
-   **Data processing:** Pandas and NumPy.
-   **Data-quality validation:** Great Expectations.
-   **Statistical analysis:** custom Python calculations and statistical
    libraries used by the drift engine.
-   **Input format:** CSV.

The frontend and backend run as separate development processes. The
basic upload-and-analyze workflow does not require a database.

## Getting started

### Prerequisites

-   Python compatible with the backend dependencies.
-   Node.js and npm compatible with the frontend.
-   Project dependencies installed.

### 1. Open the project

``` bash
cd path/to/DataWatch
```

### 2. Set up the backend

Windows PowerShell example:

``` powershell
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Use the dependency file that actually exists in the repository. Check
the installed Great Expectations version before changing it.

For a typical FastAPI app in `main.py`, the start command may be:

``` powershell
uvicorn main:app --reload
```

If the entry point differs, adjust the command to match the repository.

### 3. Set up the frontend

In a second terminal:

``` powershell
cd frontend
npm install
npm run dev
```

Open the local URL printed by Vite. The screenshots show port `5173`,
but use the URL reported by your terminal if it differs.

### 4. Check frontend/backend connectivity

Confirm that the frontend API base URL points to the running FastAPI
server. If browser requests are blocked, check the backend CORS
configuration. Keep API URLs and ports in configuration.

## Using DataWatch

1.  Open **Analyze**.
2.  Upload a reference CSV representing the baseline.
3.  Upload a current CSV representing the incoming batch.
4.  Configure the available drift threshold if required.
5.  Start analysis.
6.  Review the drift summary and feature-level results.
7.  Review the Data Quality section for failed expectations.
8.  Select a feature to inspect its metrics or category distribution.
9.  Investigate or correct the data, then run the analysis again.

Use datasets with compatible schemas for normal comparisons. Missing or
incompatible columns may produce validation errors.

## Testing with sample data

A useful smoke-test schema is:

``` text
id,salary,category,age,credit_score
```

Prepare two CSVs:

-   **Reference:** baseline salary and category distributions.
-   **Current:** a deliberate salary shift and category-frequency shift,
    while keeping age and credit score approximately similar.

For data-quality testing, create a separate current CSV with known
issues, such as null salary values, values outside the derived range, or
duplicate IDs. Keep original test files unchanged so the test can be
repeated.

Expected behavior:

-   A substantial salary distribution change should appear in numerical
    drift metrics.
-   A category-frequency change should appear in JS divergence.
-   Similar age and credit-score distributions should generally show
    smaller differences.
-   Nulls, range violations, and duplicate identifiers should be
    reported by relevant quality checks.

Exact metric values depend on the data, binning, thresholds, and
implementation. Do not expect fixed values unless both the input data
and algorithm are deterministic.

``` text
http://127.0.0.1:8000/docs
```

Use the actual host and port shown in your terminal. Results should be
calculated from submitted files rather than predefined demo values.

## Interpretation notes

-   **Drift is not the same as poor data quality.** They answer
    different questions.
-   **Drift does not prove model degradation.** The current core does
    not establish that drift caused a model's performance to decline.
-   **A small p-value is not a measure of practical importance.**
    KS-test p-values are affected by sample size.
-   **PSI and JS thresholds need context.** Treat configured thresholds
    as operational rules, not universal laws.
-   **Reference-derived ranges can flag legitimate changes.** Combine
    statistical checks with domain knowledge where needed.
-   **Identifier detection is heuristic.** Verify roles for each
    dataset.
-   **Privacy:** use datasets you are authorized to upload and avoid
    sensitive production data without appropriate safeguards.

## Limitations and future work

The current prototype focuses on CSV-based, on-demand drift and quality
analysis. Unless separately implemented, it does not include:

-   Persistent historical runs.
-   Scheduled production monitoring.
-   User accounts or authentication.
-   Email or webhook alert delivery.
-   Automatic model retraining.
-   Verified ML model-impact evaluation.
-   Production security, access controls, or deployment hardening.

Possible next steps:

1.  Add automated tests for clean data, drift, nulls, schema changes,
    and duplicate identifiers.
2.  Document and configure reference-derived numeric range rules.
3.  Persist analysis runs and trends in a database.
4.  Add model-impact analysis using a real model, suitable labels, and a
    valid evaluation dataset.
5.  Add configurable alerts and run history.
6.  Harden file-upload validation, size limits, error handling, and
    deployment security.
